# Hardening Record

| ID | Finding | Risk | Change | Verification | Residual Risk |
|----|---------|------|--------|--------------|---------------|
| H-01 | **Password hashing uses unsalted SHA256** | High — passwords crackable in seconds with rainbow tables or brute-force | Replaced `sha256` with PBKDF2-SHA256 (600k iterations, 16-byte random salt). Format: `pbkdf2:600000:<salt>:<hash>`. Legacy SHA256 hashes are still accepted for migration. | Typecheck passes; login works with seeded accounts; `hashPassword()` produces PBKDF2 format; `verifyPassword()` accepts both legacy and new format. | Reseeding the DB re-hashes passwords with PBKDF2. Old accounts using `student123`/`warden123` will work until re-seeded. |
| H-02 | **Session cookie missing security flags** | High — session token accessible via JavaScript (XSS), sent over HTTP, vulnerable to CSRF | Added `httpOnly: true`, `secure: true`, `sameSite: 'Lax'` to session cookie in `setSessionCookie()`. | Typecheck passes; login sets cookie with all three flags; existing tests pass. | In development (HTTP), `secure: true` may cause issues — only works over HTTPS in production. |
| H-03 | **IDOR: any student reads any grievance** | Critical — student A can read student B's grievance, comments, and attachments via direct ID access | Added `assertCanViewGrievance(user, row)` check to all `GET /:id`, `GET /:id/comments`, `POST /:id/comments`, `POST /:id/attachments`, and `PATCH /:id` endpoints. | Test "student cannot access another student's grievance" passes; warden access unaffected. | None for read access. Attachments use random stored names, mitigating filename enumeration. |
| H-04 | **CORS allows all origins** | High — any website can make authenticated cross-origin requests, enabling session theft | Replaced `origin: (origin) => origin ?? '*'` with a strict allowlist (`localhost:5173`, `localhost:5174`, and their `127.0.0.1` variants). Unknown origins receive empty string (rejected). | Typecheck passes; app works with Vite dev server on standard ports. | Production deployment must add the real domain to `ALLOWED_ORIGINS`. |
| H-05 | **No rate limiting on login** | High — attackers can brute-force passwords without restriction | Added in-memory sliding-window rate limiter: max 10 attempts per 15 minutes per IP. Returns 429 with `Retry-After` header on limit exceeded. Resets on successful login. | Rate limiter module created; login works normally; rate limit check is invoked before credential validation. | Rate limit state is in-memory — lost on restart. Distributed deployments need shared rate-limit store. |
| H-06 | **No security headers** | Medium — missing protections against clickjacking, MIME sniffing, etc. | Added middleware setting: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `X-XSS-Protection: 0`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`. | Headers present on all API responses. | No Content-Security-Policy header — requires careful tuning for the frontend. Add in production with appropriate directives. |
| H-07 | **Stored filename derived from user input** | Medium — could allow path traversal or filename manipulation if original name is used for storage | Changed `newStoredName()` to always generate random hex filenames (`<random>.<ext>`), removing the optional `originalName` parameter. | Typecheck passes; attachments upload and download correctly with random names. | None — stored names are now fully server-generated. |
| H-08 | **Error handler leaks internal details** | Medium — raw error messages (e.g., file paths, SQL errors) exposed to clients | Changed generic error handler to return generic "An internal server error occurred." instead of `err.message`. Original error is still logged server-side. | Test "returns 404 without leaking internals" passes; 500 responses now show generic message. | Some HttpError messages may still reveal internal logic (e.g., "Title must be at least 5 characters"). |
| H-09 | **Session expiry not enforced** | Medium — expired sessions remain valid if the cookie is still present | Added expiry check in `readSessionUser()`: if `expires_at < now`, the session row is deleted and `undefined` is returned (forcing re-auth). | Typecheck passes; existing session flow works. | Expiry is 7 days (configured in `SESSION_TTL_SECONDS`). Shorten for higher security. |
| H-10 | **No security audit logging** | Medium — cannot investigate suspicious activity after a breach | Created `logSecurityEvent()` module with structured JSON logging for: `login_success`, `login_failed`, `rate_limit_exceeded`, `file_download`, and more. Events logged to stdout with `[SECURITY]` prefix. | Test output shows `[SECURITY]` entries for all login operations. | Logs go to stdout — in production, redirect to a log aggregator or SIEM. |
| H-11 | **Students can change grievance status** | High — students should not be able to set their own grievance to "resolved" | Added guard in PATCH handler: if user is student and `status` field is provided, throw 403. Only wardens can change status. | Test "status changes work for wardens and are forbidden for students" passes. | None — role boundary properly enforced. |
| H-12 | **Logout only clears cookie, doesn't destroy session** | Medium — session token remains valid in the database after logout | Added `destroySession(db, token)` call in logout handler to delete the session row from the database before clearing the cookie. | Test "current-user works after login and fails after logout" passes (401 after logout). | None — session is properly destroyed server-side. |
| H-13 | **Test cleanup fails on Windows (EBUSY)** | Low — test infrastructure issue, not a security bug | Added `safeCleanup()` that explicitly closes the DB handle before file deletion, with a retry delay for Windows file locks. | All 14 tests pass on Windows. | N/A — development tooling only. |
